# 系统域授权与公司成员契约

本轮系统域把当前公司成员关系作为用户管理边界。平台账号 `sys_user` 可以属于多个公司；公司管理员不能通过移出或停用成员删除、停用其他公司的同一账号。公司上下文来自认证身份，客户端的公司字段不能扩大查询或写入范围。

## 有效授权

有效授权要求平台账号、租户、公司及唯一公司成员均启用且未删除。角色来自该用户在当前公司的普通绑定，以及满足 `effectFrom <= 当前时刻 < effectTo` 的临时授权；角色本身必须启用且未删除。只有有效绑定中的 `SUPER_ADMIN` 才具有超级管理员权限。缓存必须在下一临时授权生效或到期时重新求权，新写入和授权窗口判断统一使用 UTC 的 `LocalDateTime` 墙上时间，JVM 默认时区不改变结果；历史存量时间必须经受控对账后确定解释，迁移不自动改写。

普通操作者只能授予自身永久启用角色拥有的资源和数据范围，不能修改自己持有角色，不能创建或授予超级管理员角色。授权管理的超级管理员例外同样只能来自永久绑定。临时角色可以在有效时间窗内用于已授权的业务请求，但不能放大为永久授权或更长的下游临时授权。角色新增、编辑、单独绑定权限、成员绑定角色和临时授权使用同一上界。管理用户的编辑、移出、停用、重新启用、重置密码还会检查目标用户的角色上界，包括停用角色与未到期的未来临时授权，避免先停用后绕过检查。普通操作者管理自己的资料与密码应使用本人接口，修改密码需要原密码。

菜单与按钮独立绑定。页面菜单授权不自动附赠该页全部按钮；按钮授权不自动授予页面权限码。为了导航可用而补入的父级菜单不提供页面权限码。菜单与按钮均需启用且未删除，按钮还要求父菜单有效。权限目录中的 `id` 是实际菜单或按钮 ID，不能以权限码作为绑定 ID。

全局菜单、按钮与字典写入还要求全局账号的独立 `platform_admin_flag = 1`及永久授权事实，公司 `SUPER_ADMIN`不等同于平台管理员。普通账号 DTO 不能修改平台标记。首次移交由显式可信 bootstrap 指定既有有效账号并成功审计；生产启动会复核平台身份和开发种子凭据失效。已绑定的菜单/按钮权限码不能通过普通 CRUD 改名，编码迁移需独立评审并同步处理各公司既有绑定。

V13 追加实际已注册的治理页面 `/sys-manage/permission-manage`，组件为 `sys-manage/permission-manage/index`，默认 ID 为 `menu-sys-permission`，归属 `menu-sys`。新页 `perm_code = NULL`，仅向现有启用未删除、精确绑定有效 `sys:role:list` 页面导航的角色继承入口；不增加 API 权限码或 `role_button` 绑定。拥有入口不等于获得治理 API 查看或写入权限。

既有 canonical 路径保留原 ID 和全部资料；相对路径、大小写、重复和尾部斜杠按实际路由规范化核对。属主须是启用、可见且组件正确的系统管理页面。其权限码可为空，或为精确 `sys:role:list`：后一种只因继承入口的角色已经持有相同永久页面码，API 权限集合仍不扩大。其他非空码、路径歧义、稳定 ID 占用或确定性绑定 ID 冲突会在写入前阻断，不覆盖属主或替角色补权限。

该迁移在停写窗口执行，导航变更推进 `permissions` 和 `menu-tree` 数据库 epoch；随后按已审阅的环境重启合同交付。不伪造业务授权审计，也不构造依赖部署环境的 Outbox Redis 键。SQL 仅为 DML，真实 MySQL 升级测试会检查写前冲突和写后绑定失败的菜单/关联/epoch 事务结果，失败迁移不能记为成功；MySQL/Flyway 可能留下 FAILED 历史，需先核对数据及历史，再受控 repair，不能把所有迁移都当作天然完整回滚。V13 当前源码与合同已准备，最终验收以当前制品的统一构建及隔离升级回执为准。

动态路由名称稳定为 `robot-menu:菜单ID`，展示名称和路径变更不会改变路由身份。服务端按完整目录快照校验归一化的有效绝对路径，包括移动后的子树；冲突键使用 Locale.ROOT 折叠大小写，与 Admin 路由默认不区分大小写的匹配一致，原展示路径保持原值；根级 parentId 显式 null 持久化，目录深度与循环均受约束。

## 客户端版本和关联写入

Robot Admin 需要读取详情版本并随写命令提交；旧客户端缺少必填版本的请求会被拒绝，不能静默覆盖其他管理员的修改。

| 命令 | 必须携带的字段 | 空值语义 |
| --- | --- | --- |
| 角色编辑 | `revision` | 未提交权限字段保留现有绑定；`permissionIds: []` 清空绑定 |
| `PUT /sys/roles/{id}/permissions` | `revision`、`permissionIds` | `permissionIds` 不能为 null；空数组清空绑定 |
| 成员编辑或重绑角色 | `membershipRevision` | `roleIds` 不提交保留绑定；`roleIds: []` 清空当前公司绑定 |
| 成员编辑同时修改账号资料或密码 | `membershipRevision`、`revision` | 编辑密码留空表示不改密码 |
| 成员启停、移出 | `expectedRevision` = `membershipRevision` | 启停用专用DTO；移出版本放query，缺失/负值/冲突拒绝 |
| 管理员重置密码 | `expectedRevision` = 账号版本；`expectedMembershipRevision` = 成员版本 | 专用DTO，两个CAS、凭据安全版本、审计及Outbox同事务 |
| 角色删除 | query `expectedRevision` = 角色版本 | 引用/公司/权限/版本共同校验，关联与审计整体事务 |
| 菜单、按钮、字典删除 | query `expectedRevision` = 资源版本 | 删除也执行CAS，陈旧快照不会删除新状态 |
| 菜单移动 | body `revision`（兼容 `expectedRevision`别名） | 源菜单版本必填，树锁与CAS共同保护拓扑及用户意图 |
| 字典启停 | body `status`、`revision` | 缺失或陈旧版本拒绝 |
| 精准撤回临时角色 | body `expectedRevision` | 仅撤回当前公司指定grant ID，已撤回或陈旧版本冲突 |

角色详情返回 `revision`、`permissionIds`、`menuIds`、`buttonIds`。用户详情返回账号 `revision`、公司成员 `membershipRevision` 和当前公司的 `roleIds`。关联修改先比较客户端版本，再执行父聚合乐观锁写入；受影响行数不是 1 时返回并发冲突，不继续重绑关联或记录成功事件。并发冲突后客户端应重新读取详情，再由用户决定是否重试。

角色表单兼容 `name/code/sort/description`，角色读结果也返回这些只读别名及 `createTime/updateTime`；`description` 和 `remark` 目前指向同一备注字段。用户表单及读结果兼容 `deptId`，用户读结果兼容 `createTime/updateTime`。角色权限既支持统一 `permissionIds`，也支持旧 `menuIds` 加 `buttonIds`，二者不能同时提交。每批资源最多 500 项，资源 ID 不得为空、重复、超长、失效或跨公司。

角色目录绑定和全局目录写入按树锁 → 当前公司协调锁 → epoch 获取控制行。成员写入和临时角色授予先锁当前公司协调行再读引用事实，不能反向获取树锁。该协议将角色删除与成员/临授引用、成员移出与临授创建串行化；不同公司使用不同协调行。账号资料显式更新同时带 ID、有效标记与版本条件，成功审计与授权关联均由外层事务保护。

## 公司成员与共享账号

用户列表只返回当前公司未删除成员，`status/statusFlag`表示成员状态，`accountStatus`只读展示全局账号状态。角色成员清单的 `status`由账号与成员共同有效性派生。停用和重新启用只修改当前公司成员状态。移出成员撤销本公司的普通和临时授权，并保留平台账号及其他公司成员关系。内置管理员和禁止停用或移出自身的规则继续保留。

昵称、邮箱、电话和密码保存在平台账号表。公司管理 API 只能修改本公司独占账号的这些资料/密码；共享账号由本人资料和校验原密码的入口管理，公司成员编辑仍可调整本公司部门、状态及授权。独立平台管理员没有未实现的全局重置接口。

每个成员的一个主部门保存在 `sys_user_company.department_id`。V11 只回填所属公司内启用且未删除的合法旧部门，旧全局部门字段保留对账，新写入与读取不使用它。资料 Patch 省略保留：邮件、电话、成员部门显式 null 表示清空；昵称显式 null 或空白拒绝。新增账号仍要求昵称及符合统一字符/UTF-8字节规则的新密码。

成员停用或移出、账号密码变化会推进独立的安全版本；重新启用不倒退版本，因此停用前或改密前的旧会话不能恢复。普通资料变更仍使用乐观锁 `revision`，不会因此踢掉设备。

System 请求 guard 单次读取当前账号、公司、租户和唯一成员事实，精确比较 contextId、公司、账号/成员安全版本及凭据指纹；当前密码摘要不进入会话事实或诊断输出。写命令锁后的身份复验仍重新读取，不缓存或复用 guard 的旧结果。可登录上下文过滤失效账号/成员/公司/租户后，在响应中派生唯一默认公司：优先有效存储 primary，无有效主项或历史多主时按 contextId 稳定选择。该派生不回写存储标记，也不静默切换已有会话；用户明确选择的失效上下文仍须拒绝。

## 治理读取与临时角色

临时授权沿用 `userId + roleId + effectFrom + effectTo + reason`模型。创建成功返回 grant ID，未来和当前有效授予均可按该 ID 及版本精准撤回；撤回一个 grant 不影响其他授予。列表返回用户昵称、角色名称、时间窗、理由、状态和版本，名称装配不得泄漏其他公司的角色。

完整读取使用 `GET /sys/temp-authorizations/page`、`GET /sys/roles/{id}/users/page`、`GET /sys/permission-audit-logs/page`，统一返回 `list/total/page/pageSize`；历史审计支持动作、目标和起止时间筛选。旧临授/角色成员清单最多 200 项，旧审计清单最多 500 项，不能把这些有界兼容入口当作完整历史。

`GET /sys/governance-capabilities`明确区分已实现能力：数据范围、通用约束和审计治理仅提供读取；字段权限尚无模型与读取接口，read/write 均为 false；临时角色支持读取、创建和精准撤回。约束读取字段为 `ruleName/ruleType/configJson/statusFlag`，显示配置不等于规则已经执行。前端未实现的写能力不发起保存请求。

## 数据范围的当前限制

`dataScope` 支持 `self/department/department_below/all` 的配置上界。新配置的 `custom` 因缺少自定义范围模型而被拒绝；未提交数据范围的编辑不会改写已有旧值。

用户列表与用户详情已在 SQL 和目标校验中消费当前有效角色范围：`self`只可读本人，`department`只可读本人及当前成员主部门，`department_below`可读本人及合法部门子树，`all`仍只可读当前公司成员。当前成员主部门缺失、停用、属于其他公司、祖先失效或出现环时，部门范围退回本人。没有有效角色或只有未实现的 `custom`时拒绝用户读请求。本人资料/改密入口和角色绑定结构查询不受该用户读侧筛选阻断。

该实现仅覆盖用户读取，不是通用业务查询数据权限引擎，尚无字段可见、可编辑及脱敏模型。权限约束配置表目前也只提供读取，互斥、继承和二次确认没有规则执行器；基础自授与授权上界由服务中的固定安全规则执行。业务与治理模型接入前必须实现并测试实际查询、约束和字段处理，不能把显示范围或公司租户拦截器当作通用数据权限已经执行的证明。

## UTC 存量交付门

保护环境由共用 `ProductionConfiguration.protectedEnvironment` 判定：prod/pre/production profile 忽略大小写，`robot.env` 的相同标记及带连接符、下划线或空格的部署后缀同样受保护，`robot.production.enabled=true` 也会启用检查。保护环境必须持有 `sys_cache_epoch` 的精确控制行 `scope = authorization-time-utc-v1, version >= 1`。该行是时间解释合同，不是权限 epoch，不通过普通 HTTP 或 DTO 写入。

首次缺少 marker 且存在任一 `delete_flag = 1 AND status_flag = 1` 的临时授权时，启动失败；即使窗口看似已经到期，也不能假定旧无偏移时间就是 UTC。运维必须在备份副本核对旧时区、窗口和授权影响，按受控计划转换或撤回后确认合同；应用不会自动转换时间或撤销授权。没有此类旧授权时才以原子 `INSERT ... SELECT ... WHERE NOT EXISTS` 复查后初始化 marker，并回读确认登记结果；复查不满足或登记失败均阻断启动。后续重启已有 marker 可以保留新写入的合法 UTC 授予。

仅受控迁移执行方在交付核验完成后登记 `authorization-time-utc-v1` 的版本 1 并保留记录，不能盲目插入该行绕过历史对账。登记不增加表或 Flyway 版本，也不推进业务权限 epoch、写入业务授权审计或 Outbox。其他存量业务/审计日期同样保留原值并另行受控对账。

## 验证范围

正式回归包括授权事实/版本/时间窗负例、真实 MVC 参数绑定与固定 HTTP 合同、H2 的实际 MyBatis Plus CAS及事务回滚，以及隔离 MySQL 新库/V10/V5升级、完整结构合同和跨聚合竞争屏障。当前已有 MySQL 阶段结果；最终平台候选仍须按冻结源码统一重跑完整行为、质量与运行检查，不能将早期结果当作 Boot4 最终验收。

登录审计使用可恢复可信投递与 `eventId`唯一身份，System 成功持久化或证实同一事件已落库才返回成功；其他失败交上游重试。Outbox 永久非法事件隔离、完成历史逻辑归档及受控重排合同见 [数据库设计](database-design.md)和 [缓存契约](cache-and-dictionary-contract.md)。物理留存清理、通用字段/约束执行器和新的全局账号管理入口仍不属于已实现能力。
